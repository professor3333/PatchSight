# ChangedFuncs baseline on the Dunlap Go benchmark

Generated by `python -m patchsight.pipeline dunlap-baseline`; do not edit by hand. ChangedFuncs marks every function a fix commit changes as vulnerable. No LLM is involved; this checks the harness before any model is added.

## Sources

- `dunlap-llm-vulnerable-functions`: https://github.com/s3c2/llm-vulnerable-functions.git, commit `b11c663f0b9252cea2e1b1f79e5e5e0ac0dcf709`
- `dunlap-patchparser-csv`: `data/patchparser-data/patchparser-data-2023-10-31.csv`, SHA-256 `27e114745be62ea0ac225a82aa1efec0fc14dd3faa63c9e8bbdd75d563d2775e`
- Fix commits and file contents: GitHub REST API (Go's own repositories through their `github.com/golang` mirrors)

Benchmark data: Dunlap et al., "Pairing Security Advisories with Vulnerable Functions Using Open-Source LLMs", DIMVA 2024, released under Apache-2.0. Ground truth: GoVulnDB symbols as of 2023-10-26 (CC BY 4.0). This report holds counts and function names only; no source code.

## Results

280 reports, 298 fix commits (304 report-commit pairs), 588 true vulnerable symbols. The unit is a (report, function) pair, so a function changed by two commits of one report counts once. CIs are 95%, from 2,000 bootstrap resamples of reports.

| ChangedFuncs on | Candidates | True positives | Precision | Recall | F1 | Miss rate |
|---|---|---|---|---|---|---|
| Paper, as published | 2,370 | 528 | 0.22 | 0.90 | 0.35 | not reported |
| Released data, all paths | 1,760 | 472 | 0.268 (0.19 to 0.39) | 0.803 (0.76 to 0.84) | 0.402 (0.31 to 0.52) | 12.1% |
| Released data, paper's test rule | 1,190 | 470 | 0.395 (0.26 to 0.58) | 0.799 (0.76 to 0.84) | 0.529 (0.39 to 0.67) | 12.5% |
| **PatchSight pipeline**, paper's test rule | 2,330 | 525 | 0.225 (0.15 to 0.40) | 0.893 (0.86 to 0.92) | 0.360 (0.25 to 0.55) | 9.6% |

Miss rate is the share of reports where no true symbol was among the candidates.

## Agreement with the released candidates

- Candidates: PatchSight 2,330, released data 1,190 (both with the paper's test rule).
- Reports with identical candidate sets: 200 of 280; mean per-report Jaccard 0.849.
- Commits: mapped 304. Diffs computed locally because GitHub omitted the patch: 4. Files with tree-sitter parse errors: 2. Truncated commits: 0.

## Why the released CSV scores differently

The paper reports 2,370 candidates, 528 of them vulnerable. PatchSight's pipeline, run on the same commits, finds 2,330 with 525 vulnerable, which reproduces the published precision, recall and F1. The authors' released CSV holds only 1,190 candidates:

- PatchSight finds 1,170 of the CSV's 1,190 candidates (98.3%), and is a superset of the CSV in 266 of 280 reports.
- The CSV lacks 1,160 of PatchSight's candidates; 833 of them come from just 5 reports with very large fixes.
- Under the unit the authors' evaluation code uses (drop paths containing "test", group by report, commit and function) the CSV gives 1,220 units, 483 vulnerable: precision 0.396.

This is consistent with the released CSV being a subset of the paper's candidates, most likely without its largest fixes. Comparisons with the published numbers therefore use PatchSight's own candidate sets, not the CSV.

The precision interval is wide because those few very large fixes contribute most false positives. Comparisons between two systems should use a paired bootstrap over the same report resamples.
