# Evaluation

What PatchSight is measured on, what it reached, and where each number comes from. The success targets in the [proposal](proposal.md) (§8) are acceptance thresholds, not results. Each one is listed here next to what was measured. Every target that was missed is explained below the table, and so is the one not measured yet.

Four things are measured separately, as the proposal asks (§10):

- symbol extraction;
- the fix-commit locator;
- retrieval at the prompt budget;
- end-to-end verdicts.

Every evaluation set is pinned by SHA-256 in [`manifests/eval-sets.json`](../manifests/eval-sets.json), and CI fails if one changes without a deliberate re-pin ([ADR 0014](adr/0014-evaluation-sets-pinned-in-git.md)). Nothing is tuned on a test split.

How to read the Result column:

- **Met at the point estimate:** the measured value meets the threshold, but its 95% interval reaches past it.
- **Met by construction:** a check enforces the target on every push, so there is no sample to measure it on.
- **The table counts only what production runs.** Where a report exists for several databases, the table uses the newest published one; a shadow database never counts. On the Go holdout it uses the entry-point variant that [`configs/llm.toml`](../configs/llm.toml) runs.

Low recall on the Go holdout is expected. Its labels list the exported functions that call the vulnerable code, as well as that code itself. The extractor names the vulnerable functions the fix changed, so its precision is high (0.896) and its recall low. The next section covers this.

## Why each miss

### Recall after the fallback union, Go holdout

**No record built from the patch can reach this target on this holdout.** The holdout's labels hold 3,032 symbols in 83 reports, because current GoVulnDB lists the exported callers of the vulnerable code too. ChangedFuncs, which marks every function the fix changed, finds only 0.353 of them. The fallback union already keeps all of those: a low-confidence record holds every changed definition. The loss against ChangedFuncs comes from the high-confidence records, which keep only the agreed symbols.

What matters for safety is how many advisories get **no** labelled symbol at all: 1 of 83 (1.2%), the same as ChangedFuncs ([report](reports/holdout-go-holdout-v1-extract-v1-qwen3.8-27b-q4km-vs-extract-v1-gpt-oss-120b.md)). On the Dunlap test split, whose labels name the vulnerable functions themselves, the same rule reaches recall 0.887 ([ADR 0004](adr/0004-fall-back-to-the-baseline.md#test-result-2026-11-18)).

### Miss rate, high-confidence records

Three results, from three kinds of evidence, say the high-confidence tier is not safe yet:

- **Dunlap test split** ([ADR 0004](adr/0004-fall-back-to-the-baseline.md#test-result-2026-11-18)): 8 of the 115 high-confidence reports held no true symbol.
  - Six are at the patch ceiling: the labelled symbol is not among the definitions the fix changed.
  - One is a model error (`GO-2022-0706`).
  - One is a label that differs only in letter case (`GO-2022-0212`).
  - Both models see only the diff, so neither agreement nor the public-symbol condition can catch a patch-ceiling miss.
- **Go holdout** ([ADR 0010](adr/0010-go-temporal-holdout.md#result-2026-11-22)): no miss in 36. But zero misses in 36 bound the rate only below 9.6%, not below 2%. And 26 of the 36 records leave out a labelled exported function, which could give a wrong "imported, not called".
- **Injection suite** ([E8](experiments.md#e8-prompt-injection)): when the advisory text names a decoy, both model families read the same text and agree on it. 8 of 15 attacked reports got a wrong high-confidence record.

**So high confidence is withheld from every release** ([ADR 0008](adr/0008-withhold-high-confidence.md)). Every published record is low confidence and lists every changed definition. The scanner therefore never says "imported, not called", and no wrong "not called" can come from a high-confidence record.

Lifting the withholding needs a new ADR, and a rule that meets all of these:

- it is chosen on dev;
- it reaches 2% or less on data it was not chosen on;
- it covers the exported callers;
- it makes no wrong record on the injection suite.

### Fix-commit locator

**Neither heuristic comes near the target** ([E7](experiments.md#e7-locating-a-fix-commit-the-advisory-does-not-link)). The ranked heuristic gave 94 wrong answers ([report](reports/locator-masked-v1.md)):

- in 64, the fix commit the advisory links was among the commits between the same two tags, so it picked the wrong commit;
- in 30, it was not there, so it searched the wrong range.

The agent ([ADR 0011](adr/0011-fix-commit-locator-agent.md)) has no valid evaluation yet. Its first full run, on Kaggle, got HTTP 401 for every GitHub request, so that run is not counted.

**No published record depends on the locator.** Records are built only from fix commits the advisory links.

## A target that moves every night

### Nightly dead-letter rate

The table counts every night that extracted, so this result can change with each night's [operations report](reports/operations.md), and the sample is still small.

- **The first dead letter** was `GHSA-j8g8-j4j7-8j54`, on 2026-11-23. Groq rejected both requests for it, the first try and the repair, and the night's trace records both rejections.
- **The 2026-11-26 night missed the target alone: 3 dead letters of 21.**
  - All 3 prompts were over Groq's limit of 7,000 input tokens for one request (24,239, 24,275 and 7,270 tokens), and Groq refused each with HTTP 413.
  - A prompt keeps its top candidate even when that candidate alone is over the 4,600-token budget. Each of these held just one candidate, so no cut could make it smaller.
  - `GHSA-j8g8` had the same shape: one candidate, cut, refused twice at once. Its answers were not kept then, so the cause is likely but not shown.
- **The 2026-11-27 night had 2 dead letters of 16, both refused before sending.** Each prompt held one candidate over the request limit, so the run made no call for them and spent no quota.
- **The backlog is now empty.** The nights so far worked through vulnerabilities still on fallback records, including the ones the Kaggle backfill had failed on, so they drew the hardest cases. From 2026-11-28 a night extracts only that night's new or rebuilt vulnerabilities, a few at most. The rate therefore moves slowly: with 6 dead letters, it stays at 2% or more until 300 extractions have been attempted.
- **This cause is now handled, and still counts.**
  - Since 2026-11-27 the client sends no prompt over the provider's request limit. The prompt becomes a dead letter with no call and no quota spent, and the Kaggle roles, which have no such limit, can still take it.
  - That saves the quota the refusals used up (the 2026-11-26 run stopped at the daily cap with 4 vulnerabilities left), but it does not lower the rate.
  - Of the 3,505 backfill prompts, 25 (0.7%) are over the limit for the nightly role.
- **A dead letter costs precision, never safety.** The record keeps every changed definition, with the failure named in its tier reason.
- **Long answers are kept out.** Groq limits Qwen's output to 1,000 tokens a minute, so the nightly prompt holds at most 9 candidates, to keep answers under that ([ADR 0013](adr/0013-llm-extraction-in-the-nightly.md#amendment-2026-11-21-groqs-output-limit)).

## Not measured yet

### Python gold set

The declared 60 advisories were sampled and frozen before any labelling, and are labelled by the [labelling guideline](labelling-guideline.md).

- **Round 1** was labelled on 2026-11-21.
- **Round 2** relabels the same advisories blind, a week later, on or after 2026-11-28. Self-agreement between the two rounds is reported with the scores.
- **No score is run before then.** Once both rounds are done and the disagreements resolved, `gold-eval` writes `docs/reports/python-gold-v1-eval.*`. The table above then picks it up, and the target compares the gold-set F1 with the Go F1.

## Reproducing

- `make reproduce` recomputes the ChangedFuncs baseline and replays every committed Dunlap answer set through the live validator. It runs offline and needs no API key.
- `python -m patchsight.pipeline scorecard` rewrites the table above from the committed reports. A test fails if the committed table differs from that output.
- Every other report names the command that generated it at its top.
